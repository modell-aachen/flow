## Commands

All tooling runs inside devbox (direnv activates it on `cd`; `MIX_ENV=test` and `LOG_LEVEL=warning` are devbox defaults). The init hook stays cheap — it only exports `MIX_HOME`, `HEX_HOME` and `ERL_AFLAGS` and points `core.hooksPath` at `.githooks/` — and `devbox run setup` does the heavy work: hex, rebar, `mix deps.get`, `initdb` into `.devbox/virtenv/postgresql/data` (superuser `postgres`, trust auth, `max_connections=200`) and starting the `postgresql` plugin service on port 5544, waiting for `pg_isready`. It is idempotent, so re-run it whenever Postgres is not up; there is no Docker, and CI runs it as its own step before `devbox run ci`. Outside the direnv shell, prefix mix with `devbox run --`.

```bash
devbox run setup                          # mix tooling + Postgres, run this first
mix test                                  # full suite
mix test lib/flow/store_test.exs          # one file
mix test lib/flow/store_test.exs:35       # one test
mix test.interactive                      # watch mode
mix check                                 # credo --strict, format --check-formatted, sobelow
mix ci                                    # test --max-cases=8 + check (what CI runs)
devbox run docs                           # ExDoc HTML into doc/
devbox run speedrun                       # throughput harness against Postgres
devbox run consistency                    # concurrent append/consistency checker
devbox run test.stop                      # stop the Postgres service
```

The `test` alias recreates and re-migrates the test repo first, and appends `--warnings-as-errors` — a compiler warning fails the suite.

## Releases

Commit subjects must be Conventional Commits — work lands directly on `main`, so `.githooks/commit-msg` is the only gate before release-please reads the history. The devbox `init_hook` sets `core.hooksPath`, because git ignores hooks a clone ships with; it is deliberately not in `devbox run setup`, so the hook is live on shell entry without a setup run. `release-please.yml` keeps a release PR open on every push to `main`; merging it bumps `version:` in `mix.exs`, writes `CHANGELOG.md`, tags `vX.Y.Z` and cuts a GitHub release. Never edit `version:` or `.release-please-manifest.json` by hand. Pre-1.0 bumping is set by `bump-minor-pre-major` and `bump-patch-for-minor-pre-major` in `release-please-config.json`: `feat`/`fix` → patch, `!` → minor. The release PR is opened with the default `GITHUB_TOKEN`, so CI does not run on it. It rewrites the literal `version: "x.y.z"` line, so the version can never move into a `@version` attribute — anything else in `mix.exs` that wants the version has to be given it by hand.

`package/0` in `mix.exs` decides the Hex tarball and `files:` lists `lib` without `dev`, so the directory split does the carving and `exclude_patterns` is down to the two things that live in `lib/` but are not library: every `*_test.exs` and `lib/test_helper.exs`. `Ariadne.Flow.Test.Gwt` is deliberately kept — consumers test their reducers with it. `priv/` is not listed at all, because it holds only the two dev repos' migrations. `mix hex.build --unpack` is how to check.

**`docs.filter_modules` is a predicate on the module's compile source, not a namespace regex**, because HexDocs publishes whatever `mix docs` emits and `mix docs` runs in `:dev`, where `elixirc_paths` includes `dev/`. The regex it replaced, `~r/^Elixir\.Ariadne\.Flow\.(?!Examples)/`, named the one dev namespace anybody had noticed and published the other eight modules under `dev/` — the speedrun harness, its Postgres adapter and the two consistency runners. `library_module?/2` asks `module_info(:compile)[:source]` whether the module came from `lib/`, which is the same boundary `elixirc_paths(:prod)` draws, so new tooling under `dev/` needs no edit here and cannot leak. It fails closed: a module it cannot load is excluded, which under `mix docs` (project compiled, code path set) is unreachable.


## Layout conventions

- **`lib/` is the library, `dev/` is everything that must not reach a consumer.** `elixirc_paths(:prod)` is `["lib"]` and every other env is `["lib", "dev"]`, which is what keeps the examples, the speedrun harness and its Postgres adapter, the consistency runner and `Ariadne.Flow.Test.Repo` out of the compiled app — the two extra `Ecto.Repo`s in particular, which surprise anyone reflecting over repo modules. Nothing in `lib/` may reference a module under `dev/`; the compiler catches it in `:prod` and nowhere else, so it is worth knowing before the release build does. New tooling goes to `dev/`, and the Hex `files:` list needs no edit for it. Keying on `Mix.env()` is enough to cover path and git consumers as well as Hex ones, because Mix builds a dependency with `env: :prod` regardless of the parent's environment — a consumer running `mix test` still gets the `:prod` paths. `MIX_ENV=prod mix compile` is therefore the way to reproduce what a consumer compiles, and it warns that `Ariadne.Flow.Event` "was not yet implemented for any type": the examples under `dev/` are this repo's only implementations, so the shipped library legitimately has none.
- **Tests live beside their source**, not in `test/`: `test_paths: ["./lib", "./dev"]`, `test_pattern: "*_test.ex*"`. Both paths need a `test_helper.exs` — `mix test` raises on a test path without one — so `lib/test_helper.exs` runs `ExUnit.start()` and `dev/test_helper.exs` starts `Ariadne.Flow.Test.Repo`, which is the repo `dev/` owns. Name every test file `_test.exs` — a `.ex` one is compiled into the app but never collected by `mix test`, so its cases silently never run.
- **Avoid comments as much as possible.** Structure and names carry the explanation — extract a function instead of annotating a block. A comment is a last resort for a constraint the code cannot express, and it stays short.
- Directories `lib/flow/` and `dev/flow/` both map to the `Ariadne.Flow` namespace — `lib/flow/store/postgres.ex` is `Ariadne.Flow.Store.Postgres`, `dev/flow/store/speedrun.ex` is `Ariadne.Flow.Store.Speedrun`. The OTP app is `:ariadne_flow` (`:flow` is Dashbit's Flow — the Hex name and the OTP app name both collide, and two apps named `:flow` cannot coexist in one BEAM).
- Credo runs `--strict` with many opt-in checks: `SinglePipe`, `PipeChainStart`, `BlockPipe`, `StrictModuleLayout`, one alias per line, `AliasUsage` above 3 levels of nesting, no `IO.puts`/`IO.inspect` (the `.exs` scripts opt out per file). `Readability.ModuleDoc` is off because of the moduledoc policy below.
- **Every module is `@moduledoc false` until 1.0.** Module docs will be written for the public interfaces only once the API is stable enough for a 1.0 release — until then, do not add `@moduledoc` strings; the guides in `docs/` are the documentation.

## Internals the guides don't cover

**`EventReducer.evaluate/2` is the single seam between pure reducers and the store, and it knows nothing about appending.** It asks the reducer for its query, reads, deserialises, reduces, and returns `%{result:, read:}` — the reduced value plus the `Store.Read` it got it from. `Application.query/2` takes `.result` and stops; the write path goes further, and `CommandHandler` turns the read into an append condition with `AppendCondition.for_read/1` — the read's own query, after the last position it saw. One declaration therefore decides both what is read and what conflicts on write; everything docs/application.md says about concurrency falls out of `CommandHandler.handle/2`. `Store.read/3` builds no condition at all.

**Store dispatch is a behaviour, not a protocol.** `%Store{module:, config:}` and `Store` calls `module.init/read/append/consume/checkpoint/init_checkpoints/transaction/in_transaction?/telemetry_metadata/dump/load`, the callbacks of `Store.Backend` — which is also where the contract behind them (total order, atomic conditional append, isolation per config, durable checkpoints) is written down. Two backends: `Store.Postgres` and `Store.InMemory` (an Agent for tests; its `dump`/`load` are node-local and don't cross nodes). `Store` normalises the query and the append condition before dispatching, so a backend only ever sees `Query.new/1` output and an `AppendCondition` struct. `Store.read/append/init_checkpoints` wrap the backend in `:telemetry.span([:ariadne, :flow, :store, :read | :append | :init_checkpoints])`, which is what `Store.SlowOperationLogger` attaches to — `init_checkpoints` belongs there because it is a write inside the append lock's critical section, where latency serialises concurrent dispatches. `store_test.exs` is the conformance suite for the behaviour — it is parameterised over both backends.

**`consume/2` runs the reactor's handler in the calling process, inside a transaction, with the reactor's name locked** — the three things a handler that reaches back into the store depends on, and the reason `Consumption.split/2` and `Consumption.run/4` are shared rather than copied into each backend. Postgres gets all three from one `repo.transaction` holding a per-`(prefix, context, name)` advisory lock. `InMemory` cannot: a handler running inside `Agent.get_and_update` calls the agent from within the agent and deadlocks (ENA-125), so it reads the batch and writes the checkpoint in separate agent calls with the handler between them, and carries the lock — holder pid plus waiters, released by broadcasting to them — in the agent's state. That lock is process coordination and not stored data, which is why `State.restore/2` keeps the current one across a transaction rollback instead of reinstating the snapshot's, and why `lock_consume` takes over a lock whose holder is dead. The lock is re-entered rather than waited on by the process already holding it, matching an advisory lock's re-entrancy within one transaction. A test whose module reactors report to `Process.get(:inbox)` therefore plants it in the process driving the store, not in the agent.

**Reactors are configured as modules exporting `reactor/0`** because `ReactorRun` — reactor module and dispatch metadata, nothing else — has to survive `dump/1` → job system → `load/1`. That serialisation boundary is why the module name, not the struct, is the identity.

**A checkpoint is created by the append, so a run needs no resume position at all.** `Reactor.start_after_position` is a declaration; `Store.init_checkpoints/2` is where it becomes a position, and `Handoff` calls it inside the dispatch's transaction with the events appended and uncommitted — `:head` → `lowest_position(events) - 1`, an integer → itself. It must sit there and nowhere else: Postgres appends serialise on a `pg_advisory_xact_lock` held until the transaction commits, so the first dispatch to append is the first to pin a `:head` reactor, and a loser's init is a no-op against the `on_conflict: :nothing` upsert (`postgres_store_test.exs` pins this with two unboxed connections, one holding its transaction open). Everything else follows from it: `consume` resumes from `checkpoint || 0` and knows nothing about declarations, `StoredEventReactor` and `ReactorRun` carry no start position, and a run lost between commit and execution costs promptness rather than events, because the checkpoint in front of them is already committed. `Handoff.catch_up/2` initialises the same way for integer declarations, and skips a `:head` reactor with no checkpoint — the one case where a start position cannot be invented — which is why it filters on `Store.checkpoint/2` being an integer rather than on the declaration.

**Schedulers schedule, Flow executes.** `Scheduler.schedule(runs, store, opts)` is called once per dispatch, inside the transaction, with the whole run set, and returns the subset it durably enqueued; `Handoff.unscheduled/3` keeps the rest and `Application` runs them after `Store.transaction` returns. There is no default scheduler (`scheduler: nil` is "everything is Flow's"), and the safe answer to a scheduler returning something unexpected is therefore "execute it anyway" — at-least-once, never never. A claim is matched on `ReactorRun.name/1` rather than term equality, because the natural Oban scheduler returns `load(dump(run))` and the JSON round trip stringifies metadata keys — identity matching would silently unclaim every run and execute it twice. `Handoff.failures/2` closes with `catch kind, value` and not `rescue`, so an `exit` (a `GenServer.call` to a dead process is the everyday one) is contained like an exception rather than escaping past an already-committed dispatch; `kind` rides along on the failure map so `Handoff.log/1` can `Exception.format/3` it. Failure maps carry the `run`, `kind` and `stacktrace` alongside the public `name`/`position`/`reason`, so `Application` can split them by `ReactorRun.sync?/1` and raise `PostCommitError.failure/2` for the sync ones, while `Handoff.summarize/1` strips them back to what `ReactorError` and `PostCommitError` carry. `Handoff.report/1` logs **every** failure, sync included, because the raise a sync failure produces carries the dispatch's stack and not the reactor's — the log line is the only place that trace survives. `catch_up` shares the executor, which is why a raising catch-up reactor comes back as a `ReactorError` failure rather than propagating.

**Nesting is decided by `Handoff`, not by the scheduler.** `Application.dispatch/3` asks `Store.in_transaction?/1` before opening its own transaction, and the `nested: true` clause of `hand_off/3` splits the runs: sync ones are never offered to the scheduler and are executed by Flow (the only place their confirmation can come from, since the events are invisible outside the outer transaction), async ones are offered and then *dropped* rather than executed, landing after the outer commit exactly where a job row would have put them. So `ReactorRun` needs no nesting flag and a scheduler cannot get nesting wrong. Nesting is also the one case where `PostCommitError` must not say "the events are committed, never re-dispatch": the raise goes back through the caller's transaction and undoes them, so `PostCommitError.failure/2` takes the flag and swaps the advice. `Application.new/1` refuses reactors sharing a name for a related reason — one checkpoint under two reactors means each consumes events the other never sees.

**A sync reactor is awaited by Flow, not executed by it.** `sync?/1` means "the dispatch does not return until this run's checkpoint has passed the events it appended", so a scheduler may enqueue a sync run like any other as long as the job row is durable. `Consistency` (built at dispatch entry, awaited after the commit in `Application.await/3`) polls `Store.checkpoint/2` — backing off 2ms→100ms and recursing on the *unconfirmed* targets only, which is sound because a checkpoint never moves backwards — until every sync reactor's checkpoint reaches its own target, then returns `PostCommitError.timeout/2`. The wait is a `[:ariadne, :flow, :dispatch, :await]` span carrying the poll count, and `:await_timeout` is validated in `new/1` (before the transaction opens) so a bad option cannot raise after the commit. The target is **per reactor** — the highest appended position matching that reactor's filter, via `Reactor.matches?/2` on the deserialised envelopes, with reactors matching nothing dropped — because a checkpoint stays put on events the filter skips, so one global "highest appended position" would hang on every dispatch whose last event a sync reactor ignores. That is why `Consistency` carries the sync reactors' `%Reactor{}` declarations rather than their names. It is position-based because a concurrent dispatch's run may be the one that consumes these events under the per-`(prefix, context, name)` lock, leaving this dispatch's job to no-op, so job state would be the wrong thing to watch. With no scheduler the runs Flow executed have already advanced their checkpoints when the wait starts, so it confirms on the first poll and never sleeps. Failures are surfaced *before* the wait, so a sync reactor Flow saw fail raises `:failure` rather than burning the timeout; one that fails inside somebody's worker is invisible and can only time out.

**Retrying a conflict is a property of the dispatch, not of the append.** `Attempts` owns the only correct handling of `AppendConditionError` — call `append_and_hand_off` again — and is built at dispatch entry like `Consistency`, so a bad `:attempts` raises before the transaction opens. It cannot live in `CommandHandler.handle/2`: a condition failure is only meaningful relative to its transaction, and each attempt needs a new one together with the fresh read, the fresh `:head` resolution and the fresh consistency targets that follow from it — which is also why nothing has to be undone between attempts, since the `with` in `append_and_hand_off` never reaches the handoff and the conflicted attempt commits a transaction that wrote nothing. The limit collapses to 1 when the dispatch is nested, for the same reason nesting changes the handoff: the re-read would be inside the caller's snapshot, deterministically failing under repeatable read and silently deciding on shifted state under read committed. `Attempts.run/2` returns `{result, attempts_made}` because that count is the contention signal auto-retry would otherwise swallow — it is the measurement on the `[:ariadne, :flow, :dispatch]` span, whose `result` metadata separates `:conflict` (attempts exhausted) from `:error` (the command refused).

**A normalised query is a `%Query{}` struct, so "is it normalised?" is answered by the type, not by convention.** Only `Query.new/1` builds one — `%Query{filters: :all | [Filter.t]}` — and it is idempotent on a `%Query{}`, so re-normalisation is impossible rather than merely avoided; backends and `AppendCondition` only ever see the struct. `Store.read/3` runs `Query.new/1` and returns a `Store.Read` — the events, the normalised query that selected them, and `last_position` — and `AppendCondition.for_read/1` builds the condition straight from those fields. `AppendCondition.new/1` has a single clause that also takes an already-built condition: rebuilding one is free because `Query.new/1` passes the inner `%Query{}` through instead of re-optimising it. `Filter.new/1` serialises module-atom types into the store's string form, so `Filter.types` is always the store's representation and there is no separate serialise step anywhere.

**`Event.Type` is the only place that knows what a stored `type` string means**, in both directions, and neither direction needs a store. `Type.of/1` reads the declaration off the *`Event` implementation* module — `Module.concat(Event, event_module).type/0`, which `__deriving__` emits only when the derive passes `type:` — and falls back to the module name, so `of/1` owns the default and a hand-written `defimpl` pins its type by defining `type/0` itself. It reaches the implementation through `Code.ensure_compiled/1` and not `Code.ensure_loaded?/1`, because only the former waits on the parallel compiler: a filter built at compile time (`@filter Filter.new(%{types: [SomeEvent]})`) otherwise finds no implementation yet and silently falls back to the module name, which is the wrong-filter failure this whole mechanism exists to remove. An event module defined *later in the same file* is the case that stays wrong — nothing can wait for it — so filters belong in functions, as every example builds them. `CommandHandler.serialize/1`, `Filter.new/1` and `Gwt.given/1` all go through it, which is what keeps a filter, an append and a store-less envelope on the same string. `Type.module!/1` is the reverse, and it cannot be reflection on one module: it needs the whole set, so it builds `%{type => module}` from two sources unioned: the compiled set — `Event.__protocol__(:impls)` when protocols are consolidated, `Protocol.extract_impls/2` over `:code.get_path()` when they are not — **plus** every loaded impl. Test modules live only in memory and `consolidate_protocols` is off in `:test`, so the union is what makes the suite resolvable at all; it also covers the module a consolidated build cannot dispatch to, whose accurate error is the protocol's own rather than a claim that no module declares the type. The map is cached in `:persistent_term` and rebuilt once on a miss before raising, so a module compiled after the first lookup still resolves. Both raises are global once they can happen at all, which is what makes them loud and also what constrains their tests: `Type.index/1` therefore takes `{type, module}` pairs rather than modules, so a duplicate can be tested without two real impls colliding in the index every other test resolves through, and `type_test.exs` declares its not-a-string case on a module *named* like an impl (`defmodule Module.concat(Event, MistypedEvent)`) rather than a real `defimpl`, which `loaded_modules/0` would pick up and choke on.

**`Codec.deserialize/1` keeps the stored `type` and `tags` on the `%Envelope{}`** alongside the decoded event and enriched metadata. That is what `Projection.reduce/2` and `Reactor.handle/2` hand to `Filter.matches?/2` — filters match the stored form directly instead of re-encoding every event — and `Gwt.given/1` builds the same envelopes for store-less tests. `Envelope` is a plain data carrier like `Store.Record` with no `new/1`, because both of its build sites already have every field; it is the type the `EventReducer.reduce/2` callback names, so a handler and a test agree on one shape. `Filter.matches?/2` deliberately stays structural on `%{type: _, tags: _}` rather than pinning `%Envelope{}` — `Store.InMemory.State` filters raw `%Store.Record{}` structs through the same function, and the stored form is all a filter ever looks at. Only `type` and `tags` were promoted to fields: `position` and `created_at` stay *inside* `metadata`, because a handler is called with `(state, event, metadata)` and never sees the envelope, so moving them onto the struct would take them away from the two examples that read `metadata.created_at`. Promoting them is a change to the handler signature, not to the envelope. `Gwt.given/1` numbers its events from 1 so `metadata.position` is testable without a store, and passes an `%Envelope{}` through untouched — the one way a test can pin a stored `type` the event module no longer carries, which re-encoding would normalise away.

**`Query.new/1` always optimises** (`query/optimizer.ex`): it drops tag-supersets, collapses types sharing a tag constraint, and lets an unrestricted item absorb tag-restricted ones for the same type. Items with `only_last_event: true` are exempt from all of it — every rewrite assumes a broader item covers a narrower one's events, which stops holding once only the last of them is read — so they are deduplicated and otherwise passed through. Read `query/optimizer_test.exs` for the expected shape, one case per rule.

**Postgres store** (`store/postgres.ex`): `position` is a global `bigserial` giving total order. Tags live in a side table; multi-item queries become unioned subqueries ordered by position. **One tag and many tags are deliberately different queries** (`build_individual_query/2`), because since ENA-133 the store addresses views and a `GROUP BY position` that selects the event relation's other columns is only legal on a table, where `position` is a primary key Postgres can see the functional dependency on — through a view it fails with `column "type" must appear in the GROUP BY clause`. So:

- **One tag is a plain join with the tag in the `ON` clause and no grouping at all.** `(position, tag)` is the tag table's primary key, so a single tag cannot duplicate an event and there is nothing to deduplicate. This is the shape every example builds.
- **Many tags need the count, so they go through `positions_with_all_tags/3`** — `position in subquery(...)` grouped on the *tag* relation's own column, which stays view-legal. Two things in that subquery look redundant, and at least the first is not; do not "simplify" it away. **`position > ^after_position` must be repeated inside it**, because Postgres cannot push the outer bound through a `GROUP BY` and without it every bounded read re-aggregates the whole tag history. Re-measured on V03 tables at 500k events with a hot tag on every one: 0.38ms with the repetition, 1145ms without — a wider gap than the 0.2ms/143ms first recorded through the V02 views. **The repeated outer `type`/`context` predicates on a join back to the event relation are the weaker claim.** Their 116ms/0.03ms figure was measured through the views and does not reproduce standalone on tables: with two hot tags and a type matching nothing, the shipped shape and the un-repeated one both come in under 0.2ms, because `ariadne_flow_store_type_index` lets the planner evaluate the outer type predicate first and skip the subquery entirely. Drop that index and both shapes cost ~30ms, so the repetition is not what saves it. It is kept because it is free and because a plan that does evaluate the aggregate first would pay for the whole tag set inside the append lock's critical section — but treat the number as unverified on V03, and re-measure through the real query shape before relying on it.

The count-based `having` is safe against the two tag lists that would break it, because ENA-135 put them out of reach rather than teaching the query about them: `Filter.new/1` raises on `tags: []` and on a list with repeats, so `length(tags)` is always the number of distinct tags a matching event has to carry. Both forms used to reach the backends and diverge — Postgres counted them and matched nothing, `Filter.matches?/2` read them as a subset test and `InMemory` matched — and `tags: []` was the worse of the two, because `Optimizer.remove_supersets/1` treats an empty tag set as the broadest constraint and let it absorb a correct sibling filter for the same type. Neither form has a meaning distinct from an already-expressible filter, so construction rejects them and `nil` stays the only way to say "no tag constraint"; `Query.new/1` re-runs `Filter.new/1` over the optimizer's output, which stays valid because `Optimizer.build_filters/1` derives its tags from a `MapSet`. Appends serialise on a per-`(prefix, context)` `pg_advisory_xact_lock` and reactor consumption on a per-`(prefix, context, name)` one, with keys derived by `advisory_lock_key/1` from length-prefixed parts so distinct part lists cannot collide.

**The three relations the store addresses are `ariadne_flow_store`, `ariadne_flow_store_tags` and `ariadne_flow_store_reactor_checkpoints`, and as of V03 they are the physical tables** — V01 creates them under their original `modac_*` names, V02 puts `ariadne_*` views in front of them, V03 drops the views and renames the tables. The two-step rename is what gives a rolling deployment no breakage window: for the length of one release old pods address the tables and new pods the same rows through the views, which is why V02 must be deployed everywhere before V03 ships and why the upgrade path is one-directional. `@store_lock_domain`/`@checkpoint_lock_domain` stay `modac_*` **permanently**, because a conditional append is check-then-insert guarded only by the advisory lock and two pod generations hashing different domain strings would stop excluding each other; `advisory_lock_test.exs` pins the strings as documentation of that non-rename. Every version runs unconditionally, including on a fresh install: a version step cannot tell a fresh database from an existing one — V01 and V02 run immediately before V03 in the same `up/1` call — so there is one schema shape per version. Both dev repos under `priv/` have to be walked forward by hand for the harnesses to exercise the shipped schema: `flow_test_repo`'s migration is unpinned and so follows `@current_version` on its own, but `speedrun_repo` pins one migration per version (`Migration.up(version: n)`), so a new version needs a new file there or `devbox run speedrun` and `devbox run consistency` keep measuring and validating the previous schema.

**V03's asymmetry is `rollback_from(0)`, not the rename.** `up` knows its starting state exactly — it only ever runs at installed < 3, so the `modac_*` tables exist and the `ariadne_*` views were queued right before it — and the `IF EXISTS` on each `ALTER` is hygiene rather than load-bearing. `down` does not: an unreadable version rolls back from `@current_version`, so V03.down can be handed a V02 store, a V01 store or an empty schema. That is why it is the one version step that *branches*, on `Migration.renamed?/1`, and it can read that with `repo().query!` because it is the first step queued in the call and therefore still sees the pre-migration catalog. Two things make the branch necessary rather than defensive: `DROP VIEW IF EXISTS` raises `42809 wrong_object_type` on a table, so V03.down cannot open by clearing the views the way V03.up does, and its closing `CREATE OR REPLACE VIEW` needs the `modac_*` tables to exist, which on an empty schema they do not. `up` and `down` call `V02.down/1` and `V02.up/1` rather than restating the view SQL, because "restore the release-N state" is exactly V02's `up`. The constraint renames go through a `DO $$ ... EXCEPTION WHEN undefined_object $$` block since `ALTER TABLE ... RENAME CONSTRAINT` has no `IF EXISTS` for the constraint (the `IF EXISTS` it does take covers only the table); renaming the constraint carries its backing index, and the not-null constraints PG 18 auto-names `modac_*` are left alone as cosmetic catalog entries older servers do not even have. The skip-a-release guard ENA-106 proposed was dropped deliberately: under versioned migrations V02 always runs immediately before V03 in the same call, so "views missing" is unobservable, and the dangerous state — pre-V02 *pods* alive at commit time — is invisible to the schema. Rename is metadata-only, and both the `bigserial` default and the version comment travel with the table because they are wired to it by oid.

**The store schema is versioned, and the version lives in the schema itself.** `Migration.up/1` and `down/1` walk `Migration.V01`, `V02`, … one step at a time — each a `Migration.Version` implementation — and record where they stopped as a comment on the event table, which `migrated_version/1` reads back. Everything else follows from where that comment is and is not. A store installed before the versioning has none, so it reports 0: `up/1` therefore adopts it as version 1 rather than recreating anything, which is why every version's `up` stays idempotent, and `down/1` reads an unreadable version as *the newest one* — `rollback_from(0)` is `@current_version`, not `@initial_version` — so a rollback still removes a store nobody ever stamped. It has to start at the top and not the bottom: a comment is the only version record there is, and `pg_restore --no-comments`, logical replication or a stray `COMMENT ... IS NULL` can take it off a V02 store, whose views would then make V01's plain `DROP TABLE` fail with `2BP01: cannot drop table ... because other objects depend on it`. Walking down from the newest version works for both shapes because every version's `down` is `IF EXISTS`, which is the invariant a new version step owes this function. `migration_test.exs` pins all three — a full install with the comment cleared, a V02 install with the comment cleared, and a V01 install with the comment cleared.

**The comment is the one thing tying the version to a table name, and V03 renames that table, so both ends of the bookkeeping are name-aware.** `installed_version/1` reads `ariadne_flow_store` and falls back to `modac_flow_store`, which is unambiguous across all four states: pre-V02 has the comment on `modac` only, V02 has it on `modac` with `ariadne_flow_store` an uncommented view, V03 has it on `ariadne` only, and a fresh database has neither. A single static name cannot work in either direction — `ariadne_flow_store` alone resolves to the comment-less *view* on a V02 store, reads 0 and takes the adopt-unversioned path, which walks from V01 and lets `create_if_not_exists` plant fresh empty `modac_*` tables beside the real store; `modac_flow_store` alone reads 0 on a V03 store, the same failure one release later. `record_version/2` picks by the version being recorded — `>= 3` → `ariadne_flow_store`, else `modac_flow_store` — and that target always exists, because a `down` to 2 renames the table back before the comment is written.

**`Migration.renamed?/1` is a second version signal, and V03 is the first version to have one — but it is a floor, not a reading, and the two must not be confused.** `installed_version/1` is `stamped_version/1 || shape_floor/1`: when no comment is readable, `ariadne_flow_store` with `relkind = 'r'` proves the store is *at least* V03, so a store that lost its stamp to `pg_restore --no-comments` or logical replication still reports 3. Without that floor the comment-less V03 store reads 0 and `up/1` walks from V01, whose `create_if_not_exists` is a no-op but whose V02 then hits `CREATE OR REPLACE VIEW` against a *table* and dies on `42809 wrong_object_type` — loud and transactional rather than corrupting, but a regression against V02, where the same lost comment was a harmless no-op.

**Only `up/1` and `migrated_version/1` may consult the floor; `down/1` must not, and does not.** A floor is safe for `up`, which walks *upward* from it and whose steps are idempotent, and it is the best available answer for `migrated_version`. It is unsafe for `down`, which needs the *newest* possible version to sweep from: `down/1` therefore reads `stamped_version/1` and `rollback_from(nil)` is `@current_version`, so the floor can never shorten a rollback. Were `down` to take the floor instead, a comment-less V04 store would report 3, `apply_versions(3..1//-1, :down, opts)` would never call `V04.down`, and V04's objects would survive a rollback that reported success — the exact failure `rollback_from` exists to prevent, and invisible today only because `@renamed_version == @current_version`. Keeping the two attributes separate is what makes the distinction expressible; a new version step owes `down/1` an `IF EXISTS` body so the sweep from the top stays free.

**`down/1` records a version only when it read one.** `opts.version - 1` is justified only if the walk really started at a known installed version, so `record_rollback/2` writes nothing when the store was unstamped — an unstamped store stays unstamped, which is both true and idempotent. Writing it unconditionally was wrong twice over: on a schema with no store at all, `down(version: 3)` died on `COMMENT ON TABLE ... modac_flow_store` with `42P01` against the very absence `V03.down` had just been taught to tolerate; and on an unstamped V01 store it stamped `2`, after which `up/1` would skip V02, leave the `ariadne_*` views uncreated, and hand every pod on the version-2 release `relation "ariadne_flow_store" does not exist` — the state the two-step rename exists to make impossible. `record_version(_, 0)` short-circuiting is why the default full `down/1` never hit either. `Migration.qualified/2` and `Migration.quoted/1` are public because V02 hand-builds `CREATE VIEW` SQL and V03 hand-builds `ALTER ... RENAME`, both needing the same escaping `record_version/2` does; `RENAME TO` takes a bare name, which is what `quoted/1` alone is for. And because the direction has to be known before the first read, `change/0` cannot be used: a store migration is an explicit `up/0`/`down/0` pair. `installed_version/1` queries through `repo()` and runs immediately, while `execute`/`create` are queued until the runner flushes — fine as long as a version step never reads back what an earlier step in the same call wrote.

**Store-backed tests** (docs/testing.md only covers pure reducers): `Sandbox.checkout(Ariadne.Flow.Test.Repo)` plus a store on `prefix: "postgres_store_test_schema"`. `store_test.exs` runs one case set against both backends via ExUnit `parameterize`. `migration_test.exs` cannot use `Ecto.Migrator`, which runs the migration in a `Task`: the sandbox is in `:auto` mode, so that task checks out its own connection instead of the test's, and its DDL commits for real and leaks into every later test. It drives `Ecto.Migration.Runner.run/8` in the test process instead, which is the same thing the migrator does around the migration module, minus the task and the `schema_migrations` bookkeeping.
