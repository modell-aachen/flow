Where a guide and the code disagree, the examples are authoritative — e.g. `docs/event_reducer.md` shows `Projection.new/1` with `handler:` in the attrs map, but the real API is `Projection.new(attrs, handler)`.

## Commands

All tooling runs inside devbox (direnv activates it on `cd`; `MIX_ENV=test` and `LOG_LEVEL=warning` are devbox defaults). The init hook stays cheap — it only exports `MIX_HOME`, `HEX_HOME` and `ERL_AFLAGS` and points `core.hooksPath` at `.githooks/` — and `devbox run setup` does the heavy work: hex, rebar, `mix deps.get`, `initdb` into `.devbox/virtenv/postgresql/data` (superuser `postgres`, trust auth, `max_connections=200`) and starting the `postgresql` plugin service on port 5544, waiting for `pg_isready`. It is idempotent, so re-run it whenever Postgres is not up; there is no Docker, and CI runs it as its own step before `devbox run ci`. Outside the direnv shell, prefix mix with `devbox run --`.

```bash
devbox run setup                          # mix tooling + Postgres, run this first
mix test                                  # full suite
mix test lib/flow/store_test.exs          # one file
mix test lib/flow/store_test.exs:35       # one test
mix test.interactive                      # watch mode
mix check                                 # credo --strict, format --check-formatted, sobelow
mix ci                                    # test --max-cases=8 + check (what CI runs)
devbox run docs                           # ExDoc HTML into doc/
devbox run speedrun                       # throughput harness against Postgres
devbox run consistency                    # concurrent append/consistency checker
devbox run test.stop                      # stop the Postgres service
```

The `test` alias recreates and re-migrates the test repo first, and appends `--warnings-as-errors` — a compiler warning fails the suite.

## Releases

Commit subjects must be Conventional Commits — work lands directly on `main`, so `.githooks/commit-msg` is the only gate before release-please reads the history. The devbox `init_hook` sets `core.hooksPath`, because git ignores hooks a clone ships with; it is deliberately not in `devbox run setup`, so the hook is live on shell entry without a setup run. `release-please.yml` keeps a release PR open on every push to `main`; merging it bumps `version:` in `mix.exs`, writes `CHANGELOG.md`, tags `vX.Y.Z` and cuts a GitHub release. Never edit `version:` or `.release-please-manifest.json` by hand. Pre-1.0 bumping is set by `bump-minor-pre-major` and `bump-patch-for-minor-pre-major` in `release-please-config.json`: `feat`/`fix` → patch, `!` → minor. The release PR is opened with the default `GITHUB_TOKEN`, so CI does not run on it.

## Layout conventions

- **Tests live beside their source in `lib/`**, not in `test/`: `test_paths: ["./lib"]`, `test_pattern: "*_test.ex*"`, helper at `lib/test_helper.exs`. Name every test file `_test.exs` — a `.ex` one is compiled into the app but never collected by `mix test`, so its cases silently never run.
- **Avoid comments as much as possible.** Structure and names carry the explanation — extract a function instead of annotating a block. A comment is a last resort for a constraint the code cannot express, and it stays short.
- Directory `lib/flow/` maps to the `Ariadne.Flow` namespace — `lib/flow/store/postgres.ex` is `Ariadne.Flow.Store.Postgres`. The OTP app is `:flow`.
- Credo runs `--strict` with many opt-in checks: `SinglePipe`, `PipeChainStart`, `BlockPipe`, `StrictModuleLayout`, one alias per line, `AliasUsage` above 3 levels of nesting, no `IO.puts`/`IO.inspect` (the `.exs` scripts opt out per file). `Readability.ModuleDoc` is off because of the moduledoc policy below.
- **Every module is `@moduledoc false` until 1.0.** Module docs will be written for the public interfaces only once the API is stable enough for a 1.0 release — until then, do not add `@moduledoc` strings; the guides in `docs/` are the documentation.

## Internals the guides don't cover

**`EventReducer.evaluate/2` is the single seam between pure reducers and the store, and it knows nothing about appending.** It asks the reducer for its query, reads, deserialises, reduces, and returns `%{result:, read:}` — the reduced value plus the `Store.Read` it got it from. `Application.query/2` takes `.result` and stops; the write path goes further, and `CommandHandler` turns the read into an append condition with `AppendCondition.for_read/1` — the read's own query, after the last position it saw. One declaration therefore decides both what is read and what conflicts on write; everything docs/application.md says about concurrency falls out of `CommandHandler.handle/2`. `Store.read/3` builds no condition at all.

**Store dispatch is a behaviour, not a protocol.** `%Store{module:, config:}` and `Store` calls `module.init/read/append/consume/checkpoint/transaction/in_transaction?/telemetry_metadata/dump/load`, the callbacks of `Store.Backend` — which is also where the contract behind them (total order, atomic conditional append, isolation per config, durable checkpoints) is written down. Two backends: `Store.Postgres` and `Store.InMemory` (an Agent for tests; its `dump`/`load` are node-local and don't cross nodes). `Store` normalises the query and the append condition before dispatching, so a backend only ever sees `Query.new/1` output and an `AppendCondition` struct. `Store.read/append` wrap the backend in `:telemetry.span([:ariadne, :flow, :store, :read | :append])`, which is what `Store.SlowOperationLogger` attaches to. `store_test.exs` is the conformance suite for the behaviour — it is parameterised over both backends.

**Reactors are configured as modules exporting `reactor/0`** because `ReactorRun` — reactor module, resume position, dispatch metadata — has to survive `dump/1` → job system → `load/1`. That serialisation boundary is why the module name, not the struct, is the identity. `ReactorRun.nested` is the exception that is deliberately *not* dumped: it is a fact about the dispatch, and a run on its way to a job system is executed outside whatever transaction that dispatch was nested in.

**`Reactor.start_after_position` is a declaration, `ReactorRun.start_after_position` is a position, and `Handoff` is where one becomes the other.** `:head` (the default) has no store-independent meaning — "now" is whatever the run builder knows about — so `ReactorRun.new/1` raises on it rather than inventing a fallback, which is also what keeps `:head` out of a dumped run whose worker's "now" is a different one. `Handoff.hand_off/3` resolves it to `lowest_position(events) - 1` and `Handoff.catch_up/2` to the reactor's checkpoint, dropping the reactor when there is none. Integer declarations are passed through **unchanged** by both, which is the whole point: a `start_after_position: 0` reactor gets the store's history from whoever runs it first, so boot-time `catch_up` and a dispatch that beats it there are not a race with two different outcomes. `Store.consume` still owns the resolution that matters (`checkpoint || start_after_position`), so a stale run can never move a checkpoint backwards. `Handoff` builds the runs for both entry points and drives them through the same engine call, which is why `catch_up` needed no engine contract of its own — only `Application.catch_up/2` returning `{:error, %ReactorError{}}` as a value where a dispatch raises, because nothing was appended and retrying a catch-up is always safe.

**A sync reactor is awaited by Flow, not executed by it.** `sync?/1` means "the dispatch does not return until this run's checkpoint has passed the events it appended", so an engine may enqueue a sync run like any other as long as the job row is durable. `Consistency` (built at dispatch entry, awaited after the commit in `Application.await/3`) polls `Store.checkpoint/2` — backing off 2ms→100ms and recursing on the *unconfirmed* targets only, which is sound because a checkpoint never moves backwards — until every sync reactor's checkpoint reaches its own target, then raises `ConsistencyTimeoutError`. The wait is a `[:ariadne, :flow, :dispatch, :await]` span carrying the poll count, and `:await_timeout` is validated in `new/1` (before the transaction opens) so a bad option cannot raise after the commit. The target is **per reactor** — the highest appended position matching that reactor's filter, via `Reactor.matches?/2` on the deserialised envelopes, with reactors matching nothing dropped — because a checkpoint stays put on events the filter skips, so one global "highest appended position" would hang on every dispatch whose last event a sync reactor ignores. That is why `Consistency` carries the sync reactors' `%Reactor{}` declarations rather than their names. It is position-based because a concurrent dispatch's run may be the one that consumes these events under the per-`(prefix, context, name)` lock, leaving this dispatch's job to no-op, so job state would be the wrong thing to watch. An engine executing runs inline therefore needs no changes: its checkpoint committed with the events, so the first poll confirms. The one case that cannot be awaited is a dispatch nested in a caller's transaction — nothing outside it can see the events or the job row — which is why `Application.dispatch/3` asks `Store.in_transaction?/1` *before* opening its own transaction and `ReactorRun.inline?/1` (`nested and sync?`) tells the engine to execute that run inline instead.

**Retrying a conflict is a property of the dispatch, not of the append.** `Attempts` owns the only correct handling of `AppendConditionError` — call `append_and_hand_off` again — and is built at dispatch entry like `Consistency`, so a bad `:attempts` raises before the transaction opens. It cannot live in `CommandHandler.handle/2`: a condition failure is only meaningful relative to its transaction, and each attempt needs a new one together with the fresh read, the fresh `:head` resolution and the fresh consistency targets that follow from it — which is also why nothing has to be undone between attempts, since the `with` in `append_and_hand_off` never reaches the handoff and the conflicted attempt commits a transaction that wrote nothing. The limit collapses to 1 when the dispatch is nested, for the reason `ReactorRun.inline?/1` exists: the re-read would be inside the caller's snapshot, deterministically failing under repeatable read and silently deciding on shifted state under read committed. `Attempts.run/2` returns `{result, attempts_made}` because that count is the contention signal auto-retry would otherwise swallow — it is the measurement on the `[:ariadne, :flow, :dispatch]` span, whose `result` metadata separates `:conflict` (attempts exhausted) from `:error` (the command refused).

**A normalised query is a `%Query{}` struct, so "is it normalised?" is answered by the type, not by convention.** Only `Query.new/1` builds one — `%Query{items: :all | [Item.t]}` — and it is idempotent on a `%Query{}`, so re-normalisation is impossible rather than merely avoided; backends and `AppendCondition` only ever see the struct. `Store.read/3` runs `Query.new/1` and returns a `Store.Read` — the events, the normalised query that selected them, and `last_position` — and `AppendCondition.for_read/1` builds the condition straight from those fields. `AppendCondition.new/1` has a single clause that also takes an already-built condition: rebuilding one is free because `Query.new/1` passes the inner `%Query{}` through instead of re-optimising it. `Query.Item.new/1` serialises module-atom types into the store's string form, so `Item.types` is always the store's representation and there is no separate serialise step anywhere.

**`Store.Event.Type` is the only place that knows what a stored `type` string means**, in both directions, and neither direction needs a store. `Type.of/1` reads the declaration off the *`Encoder` implementation* module — `Module.concat(Encoder, event_module).type/0`, which `__deriving__` emits only when the derive passes `type:` — and falls back to the module name, so `of/1` owns the default and a hand-written `defimpl` pins its type by defining `type/0` itself. It reaches the implementation through `Code.ensure_compiled/1` and not `Code.ensure_loaded?/1`, because only the former waits on the parallel compiler: a filter built at compile time (`@item Query.Item.new(%{types: [SomeEvent]})`) otherwise finds no implementation yet and silently falls back to the module name, which is the wrong-filter failure this whole mechanism exists to remove. An event module defined *later in the same file* is the case that stays wrong — nothing can wait for it — so filters belong in functions, as every example builds them. `CommandHandler.serialize/1`, `Query.Item.new/1` and `Gwt.given/1` all go through it, which is what keeps a filter, an append and a store-less envelope on the same string. `Type.module!/1` is the reverse, and it cannot be reflection on one module: it needs the whole set, so it builds `%{type => module}` from two sources unioned: the compiled set — `Encoder.__protocol__(:impls)` when protocols are consolidated, `Protocol.extract_impls/2` over `:code.get_path()` when they are not — **plus** every loaded impl. Test modules live only in memory and `consolidate_protocols` is off in `:test`, so the union is what makes the suite resolvable at all; it also covers the module a consolidated build cannot dispatch to, whose accurate error is the protocol's own rather than a claim that no module declares the type. The map is cached in `:persistent_term` and rebuilt once on a miss before raising, so a module compiled after the first lookup still resolves. Both raises are global once they can happen at all, which is what makes them loud and also what constrains their tests: `Type.index/1` therefore takes `{type, module}` pairs rather than modules, so a duplicate can be tested without two real impls colliding in the index every other test resolves through, and `type_test.exs` declares its not-a-string case on a module *named* like an impl (`defmodule Module.concat(Encoder, MistypedEvent)`) rather than a real `defimpl`, which `loaded_modules/0` would pick up and choke on.

**`Codec.deserialize/1` keeps the stored `type` and `tags` on the envelope** alongside the decoded event and enriched metadata. That is what `Projection.reduce/2` and `Reactor.handle/2` hand to `Query.Item.matches?/2` — filters match the stored form directly instead of re-encoding every event — and `Gwt.given/1` builds the same envelopes for store-less tests.

**`Query.new/1` always optimises** (`query/optimizer.ex`): it drops tag-supersets, collapses types sharing a tag constraint, and lets an unrestricted item absorb tag-restricted ones for the same type. Items with `only_last_event: true` are exempt from all of it — every rewrite assumes a broader item covers a narrower one's events, which stops holding once only the last of them is read — so they are deduplicated and otherwise passed through. Read `query/optimizer_test.exs` for the expected shape, one case per rule.

**Postgres store** (`store/postgres/query.ex`): `position` is a global `bigserial` giving total order. Tags live in a side table, so AND-semantics come from a join plus `group_by(position)` / `having(count(tag) == length(tags))`; multi-item queries become unioned subqueries ordered by position. Appends serialise on a per-`(prefix, context)` `pg_advisory_xact_lock` and reactor consumption on a per-`(prefix, context, name)` one, with keys derived by `advisory_lock_key/1` from length-prefixed parts so distinct part lists cannot collide.

**Store-backed tests** (docs/testing.md only covers pure reducers): `Sandbox.checkout(Ariadne.Flow.Test.Repo)` plus a store on `prefix: "postgres_store_test_schema"`. `store_test.exs` runs one case set against both backends via ExUnit `parameterize`.
